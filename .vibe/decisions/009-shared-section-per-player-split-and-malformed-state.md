# Splitting a shared p1./p2. section into per-player elements; malformed prefixing gets a neutral, non-guessed placeholder

**Context:** Backlog item 011. A real Ikemen GO section (`[Lifebar]`, `[Powerbar]`, `[Face]`, `[Name]`) holds both players' data in one section, distinguished only by a `p1.`/`p2.` key prefix on every entry — unlike the classic MUGEN convention where the player is already in the section name and no such prefix exists inside it. The elements panel's existing "one section = one element" assumption (`.vibe/decisions/004`) needs to become "one section = one **or two** elements" without disturbing the classic case at all.

**Decision:**
- **Classification is entry-shape-driven, never name-driven**: a section is `unprefixed` (no entry key starts with `p1.`/`p2.`, case-insensitive) → single element exactly as today; `per-player` (both `p1.`/`p2.` present, no disqualifying unprefixed entry) → split into two elements, named `"{section name} (P1)"` / `"(P2)"`, each computed from only that player's own entries with the prefix stripped; otherwise `malformed` (a disqualifying unprefixed entry alongside `p1.`/`p2.` ones, or only one player's prefix present at all) → a single diagnostic element, never a guessed or blended layout.
- **"Unprefixed" only disqualifies a split when it's layout-relevant.** Real Ikemen GO files (confirmed against the VHD fixture) legitimately mix `p1.`/`p2.` data with section-wide, non-positional settings inside the very same section (`[Powerbar]`'s `level1.snd`/`level2.snd`/`level3.snd`), and Simul-mode sections add an unrelated third/fourth-player prefix (`p3.`/`p4.`) this item deliberately doesn't split (out of scope). Neither can produce a plausible-but-wrong split layout by itself — `computeElementLayout` already silently ignores any key that isn't `pos`/`N.spr`/`N.offset`, regardless of prefix — so only an *unprefixed* entry shaped like one of those three disqualifies a split into `malformed`; every other unprefixed or differently-prefixed key is inert noise the split tolerates, the same way a single-element section already tolerates it today.
- **A malformed element is anchored at a fixed neutral origin `(0, 0)` with no sprite layers**, even when one player's data is fully present (the one-sided case). Using that player's own `pos` would produce a box that looks like a legitimate, verified position — indistinguishable at a glance from a correctly split element — which is a worse outcome for a troubleshooting author than an obviously-placeholder one. The overlay's hover title still explains the exact condition (mixed vs. one-sided) so the fix is discoverable.
- **Visual treatment**: a new `elements-panel__overlay--malformed-prefix` style — a solid **double**-line `--wuik-color-danger` border — added alongside the three existing states (`--no-sprite`, `--waiting`, `--unresolved`, all single dashed borders). Reusing the danger hue keeps "this is an error" consistent, while the double-line geometry (not just a tooltip) keeps it distinguishable at a glance from `--unresolved` (a single bad sprite *reference* against an otherwise-fine layout) without inventing a token this app's palette doesn't have. `.is-selected`'s solid accent border overrides it exactly the same way selection already overrides the three pre-existing states — no new stacking rule.
- **No separate list-panel badge**: the canvas overlay plus its title is the sole carrier of the diagnostic, matching how the three pre-existing states already work (list items never carry error styling of their own).
- **Simulation slots stay keyed to the section index**, not the flattened per-player element index — the sections `detectSimulatableSlots` matches (`P1 Life Bar`-style) never carry a `p1.`/`p2.` prefix internally and therefore never split, so this needs no change, only care that the flattened rendering loop still looks slots up by original section index.

**Reason:** A lifebar-preview tool's core value is telling a troubleshooting author exactly which of several distinct broken states they're looking at (`.vibe/decisions/004`'s founding principle, extended here one level up from "per-layer resolution" to "per-section prefix shape"). Never rendering a plausible-looking box from partial data keeps that promise intact — a wrong-but-confident-looking layout would be strictly worse than today's un-split single element.

**Rejected alternatives:**
- *Position a one-sided-prefix element using that player's own `pos`*: rejected — looks like a verified, correct position rather than a diagnostic placeholder, actively misleading for the one state (partial data) where it would be most tempting to trust it.
- *Reuse `--unresolved`'s exact dashed-danger style for the new malformed state*: rejected by both consulting experts — collapses two different kinds of error (a single bad sprite reference vs. an entire section whose per-player structure can't be determined at all) into one visual, defeating the "diagnostic, not one generic placeholder" precedent this app already committed to.
- *A list-panel badge/icon for the malformed state*: rejected — no existing state carries one; adding it here alone would be an inconsistent, one-off enrichment outside this item's scope.
