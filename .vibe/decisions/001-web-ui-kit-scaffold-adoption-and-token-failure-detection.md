# Adopt `web-ui-kit`'s app shell as a minimal scaffold, and detect a failed tokens stylesheet by probing a known custom property

**Context:** Backlog item 001 adopts the org's shared design system (`@openkakutou/web-ui-kit`) before any real screen exists in this repo — only a placeholder version string is displayed today. `web-ui-kit`'s `<wuik-app-shell>` provides toolbar, sidebar, and main-content regions; only the toolbar (title + version) has anything to show right now. Unlike the sibling `character-viewer-web`'s equivalent item, this item's acceptance criteria also require a visible error state — not a blank page — if the tokens stylesheet fails to load at runtime.

**Decision:**
- Use `<wuik-app-shell>` as the root frame, with `<wuik-toolbar>` (holding the app title + version, `role="banner"`) slotted into the toolbar region and an empty native `<main>` landmark for future content (items 002+). No sidebar content is slotted yet — mirrors `character-viewer-web`'s own adoption (`.vibe/decisions/003-app-shell-adoption-scope.md` in that repo) and its reasoning: an empty sidebar reads as unfinished chrome, omitting it does not.
- Ship token-driven styling only — no hardcoded colors/spacing anywhere in the app's own CSS — so both themes work correctly the instant `data-theme="dark"` is set on an ancestor, even though no in-app toggle exists yet. This satisfies this item's stricter "including light/dark" wording (vs. the sibling item's "color/spacing/typography" only) as "verified to switch correctly," not "a toggle UI ships now."
- Detect a failed tokens stylesheet load by probing whether a known token (`--wuik-color-bg`) resolves to a real value via `getComputedStyle` on the root element, immediately before mounting the shell. If it doesn't resolve, skip mounting the shell entirely (it depends on those same tokens for its own layout and would render broken/unstyled) and show a plain, dependency-free error message instead — no `web-ui-kit` tokens, custom elements, or ARIA live-region roles in that fallback, since it must remain visible in the exact scenario where those failed.
- The probe runs after `window`'s `load` event (a no-op wait if it already fired), not immediately on module execution. Verified against the actual built output: Vite emits the app's `<script type="module">` tag *before* the tokens `<link rel="stylesheet">` tag, and a module script isn't parser-blocked by a stylesheet that follows it the way a classic script would be — probing immediately would race the still-loading stylesheet and could false-negative. `load` is spec-guaranteed to fire only once every stylesheet referenced at parse time has settled, which removes the race without a bespoke per-stylesheet event listener.
- Mirror the app title + version into `document.title`, so the tab itself identifies which OpenKakutou viewer app is open — useful once several sibling viewer apps are open in adjacent tabs.

**Reason:** Matches the item's brief ("adopt before building any real screen") without inventing UI that has no purpose yet, while directly satisfying the "never a blank page" requirement with the simplest mechanism that doesn't itself depend on the thing it's checking for. Informed by consulting `vibe:expert-frontend-design` (minimal scaffold scope, fallback must not depend on the tokens it's checking) and `vibe:expert-ui-ux` (specific, actionable error copy over a generic message; no retry button needed since a reload fixes a static-asset failure; document title should identify the app).

**Rejected alternatives:**
- *Add a retry button to the error state* — rejected: over-engineering for a failed static-asset load, which a page reload already fixes; the message points the user at that instead.
- *Style the error fallback with `--wuik-*` tokens, falling back gracefully via CSS `var()`'s own undefined-property behavior* — rejected: technically survivable (an unresolved custom property leaves the declaration ignored, not blank), but a plain, dependency-free fallback is simpler to reason about and matches the explicit expert recommendation to never reference the very tokens whose absence is being handled.
- *Listen for the stylesheet `<link>`'s own `load`/`error` event before probing* — rejected: this app doesn't hold a reference to that element (it's injected by a bare `import "...tokens.css"`, not authored markup), and `window`'s `load` event already gives the same guarantee with no extra wiring.
