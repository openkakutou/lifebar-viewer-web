# Lifebar input: folder-only selection, own parser warns on unrecognized sections

**Context:** Backlog item 002 needs a file-input mechanism and a parser for the lifebar `.def`-style format. No shared `lifebar` library exists to follow (roadmap decision `009`), and the sibling `lifebar-editor` app already shipped its own, deliberately separate parser for the same format (its item 002, `.vibe/decisions/002-lifebar-parser-data-model-and-error-scope.md`) with a silently-retain-everything philosophy. Two choices needed to be made explicitly for this app: the input mechanism, and whether to diverge from the sibling parser's retention philosophy.

**Decision:**
- Folder selection (`<input webkitdirectory>` plus a drag-and-drop zone walking `DataTransferItem.webkitGetAsEntry()`) is the **only** input path, matching the acceptance criteria — there is deliberately no single-file fallback, even though `wuik-file-drop-zone` (the shared kit's existing component) only supports single/multi-file picking. This app builds its own local folder-picker view instead of reusing that component, since the kit has no directory-selection support to extend it with in scope.
- The data model (ordered-array sections/entries, case-insensitive name matching, original casing preserved) mirrors `lifebar-editor`'s own model — same reasoning applies here (duplicate section/key names are a real authoring pattern; ordered arrays never silently collapse them) — but the parser adds a concept `lifebar-editor`'s does not need: a curated, best-effort set of **recognized** top-level section-name families (life bar / power bar / face / name / win icons / match wins / round time / combo, per this app's own project scope), documented in one module. A syntactically valid section whose name matches none of them is **excluded from the typed result and reported as a line-numbered warning**, rather than silently retained.
- This is a deliberate product-level divergence from the editor's silent-retention choice, not an oversight: `lifebar-editor` must round-trip a file faithfully on save, so silently keeping everything it doesn't understand is exactly correct there. This app never writes anything back — it only ever displays what it recognizes — so a section it can't display is more useful to the Product Owner as a visible warning (something didn't get shown) than as data quietly ignored deeper in the pipeline. Malformed syntax (not just an unrecognized name) is still a hard parse error, same as the editor.
- The exact recognized-name patterns are a best-effort approximation of the real MUGEN/Ikemen lifebar format (no real-file corpus available yet) and are expected to be corrected once item 006 (fixture-driven compatibility testing against real lifebar files) runs — this item does not block on that.

**Reason:** Folder-only input is what the acceptance criteria ask for outright (a single-file input cannot reach sibling assets in a distributed lifebar pack, per the browser sandboxing constraint already documented in the backlog item's own Notes). The warn-on-unrecognized behavior follows directly from this app being read-only/preview-only: a silently dropped section is invisible to the one person (the Product Owner, previewing a lifebar) who could act on it, whereas the editor's save-path correctness need doesn't apply here at all.

**Rejected alternatives:**
- **Reuse/extend `wuik-file-drop-zone` with directory support**: rejected for this item — that component lives in a separate repo (`web-ui-kit`) with its own backlog; extending it is out of this item's scope and would block this item on a cross-repo change that isn't otherwise needed.
- **Silently retain every unrecognized section, matching `lifebar-editor` exactly**: rejected — this item's own acceptance criteria explicitly require a warning on skip, and the two apps' parsers are already independent by roadmap decision `009`, so there is no shared-code cost to diverging where the product need differs.
