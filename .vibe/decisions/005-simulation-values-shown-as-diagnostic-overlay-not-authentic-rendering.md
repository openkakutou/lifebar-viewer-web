# Simulated life/power/combo values are shown as a diagnostic overlay, not authentic MUGEN rendering

**Context:** Backlog item 005 wants sliders that visibly change the life bar, power bar, and combo counter in the existing preview (item 004). That preview is a purely static sprite-layer composite with no concept of a value at all — no fill-bar/percentage-scaling logic (needed to authentically shrink/grow a life or power bar sprite) and no bitmap-font/text rendering (needed to authentically draw combo digit sprites). Building either authentically means guessing at real MUGEN `range.x`/`front.spr`-style bar-fill semantics and `.fnt` bitmap-font parsing with no fixture-driven validation available yet — that hardening is backlog item 006, already scoped and deliberately deferred (see `known-sections.ts`'s own "best-effort... not yet validated against a real-file corpus" note, which this decision extends the same risk posture to).

**Decision:** A simulated value is shown as a clearly-distinct **diagnostic overlay** on top of the element's own real, already-rendered sprite layers — never mixed into or replacing the real rendering. Life/power: a semi-transparent fill rectangle in `--wuik-color-warning` (never `--wuik-color-accent`, already used for selection, or `--wuik-color-danger`, already used for an unresolved reference) with a diagonal-stripe pattern so the cue survives regardless of what hue the underlying sprite happens to use, growing from the element box's left edge, width proportional to the percentage. Combo: a small numeric chip with a guaranteed-contrast background, positioned at the element box's corner. Detected only for sections the loaded file actually defines (no disabled/ghosted control for an absent section) — life/power sliders are per-player (`P1`/`P2`, whichever the file has), each paired with a numeric input bound to the same value for precise, keyboard-accessible entry. Values: life/power default to 100 (a freshly-loaded, undamaged bar is the more useful diagnostic starting point than an empty one) and clamp to 0–100; combo defaults to 0 and clamps to 0–50 (MUGEN itself has no real combo ceiling, but an unbounded slider crushes the 1–20 range most diagnostic testing actually uses into a few pixels of drag precision).

**Reason:** This app's own purpose is a diagnostic previewer ("so a lifebar's construction can be checked... without a real match running"), not a pixel-perfect game renderer — a clearly-synthetic diagnostic indicator serves that purpose honestly. Attempting authentic rendering now would mean shipping unverified guesses about real MUGEN internals presented as if they were correct, exactly the kind of unvalidated assumption item 006 exists to catch and fix properly later, with real fixtures.

**Rejected alternatives:**
- **Authentic pixel-perfect rendering (real bar-fill scaling, real bitmap-font digits) now:** rejected — no fixture-driven validation exists yet for this app's MUGEN format support at all; inventing fill-bar/font semantics from memory risks shipping a confidently-wrong "reference" implementation, worse than an honestly-labeled approximation.
- **Reuse the existing selection-highlight overlay's visual language (accent-colored border) for the simulated-value overlay:** rejected — plan consultation flagged that a user couldn't tell "this element is selected" from "this element has a simulated value" when both are visible on the same element at once; the two need visually independent cues.
- **An unbounded or very large combo slider max:** rejected — the useful low range where most diagnostic testing happens would be crushed into a few pixels of drag precision, per plan consultation.
