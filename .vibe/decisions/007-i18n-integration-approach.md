# Localization (i18n) integration approach

**Context:** Backlog item 008 adopts the shared `web-ui-kit` i18next integration layer (`initI18n`, `t`, `<wuik-locale-switcher>`, roadmap decision `023`) so this app's UI strings move into `src/i18n/en.json`/`fr.json` and the user can switch language live, without a page reload, with the choice persisted across reloads.

**Decision:**
- The app's brand name ("Lifebar Viewer") is left untranslated, treated as a proper noun — only descriptive text, status/error messages, and accessible labels move into the catalogs.
- A thin wrapper (`src/i18n/i18n.ts`) mirrors `web-ui-kit`'s own `t(key, defaultValue, vars?)` contract exactly: it returns the interpolated `defaultValue` verbatim whenever this app hasn't called `initI18n` yet (or the key is missing), and otherwise delegates to the active instance's own `t()` under this app's namespace. Every call site's `defaultValue` is kept identical, character for character, to the English catalog entry for that key, so a render produces the same text whether or not `initI18n` has run yet — existing tests that never call `initI18n` keep asserting plain English text unchanged.
- `initI18n` is only ever called from the real bootstrap (`mount()` in `main.ts`), awaited before the first `renderApp` call — never from `renderApp` itself, which stays synchronous so the existing test suite can keep calling it directly and assert on the immediate result. Production users therefore never see an English flash before their persisted locale resolves; test code that only calls `renderApp` directly gets deterministic English defaults.
- Live locale-switching is handled at two levels, not by every render function subscribing individually: `main.ts` subscribes once to `onLocaleChange` and re-invokes its own existing `refreshElementsPanel`/`refreshSimulationControls` closures (already the app's normal re-render path on every data change) plus updates the toolbar/error text — reusing the state objects already threaded through them, so the current element selection and simulated values survive a language switch untouched. The long-lived folder-input view (`lifebar-folder-input-view.ts`) subscribes once, internally, to re-render its own currently-displayed status/error text from a small stored status descriptor rather than a pre-formatted string, so an already-shown message re-renders correctly in the new language.
- Pluralized fragments ("1 section" vs "3 sections", "1 group" vs "2 groups") are composed by picking an already-translated singular/plural noun and interpolating it into a translated sentence template — not i18next's automatic `_one`/`_other` key-suffix pluralization. This keeps the sentence deterministic and correct whether or not a real i18next instance is active yet (the fallback path only does simple `{{var}}` substitution, no plural-rule evaluation).
- This app passes its own `storageKey` (`"lifebar-viewer-web-locale"`) to `initI18n` instead of the shared default (`"wuik-locale"`): every OpenKakutou web app is deployed as its own GitHub Pages project site under the same `openkakutou.github.io` origin, and `localStorage` is scoped per-origin, not per-path — sharing the default key would mean a language choice made in one app silently forces the same language in every other OpenKakutou app sharing that origin.

**Reason:** These choices keep the existing, already-large test suite passing with minimal, surgical edits (the fallback-mirrors-default-value property is what makes that possible), avoid a class of re-render/subscription-leak bugs that per-component locale subscriptions would introduce in a codebase that already re-renders the elements panel and simulation controls very frequently, and prevent a real cross-app localStorage collision this org's own GitHub Pages deployment topology makes concrete, not hypothetical.

**Rejected alternatives:**
- *Every render function subscribes to `onLocaleChange` itself* — rejected: `renderElementsPanel`/`renderSimulationControls` are already re-invoked on every value change; a fresh internal subscription on every call would accumulate indefinitely over an app session instead of staying at one subscription for the view's whole lifetime.
- *i18next's automatic `_one`/`_other` pluralization* — rejected here specifically for the fallback (pre-`initI18n`) path, which only does literal `{{var}}` substitution and cannot evaluate CLDR plural rules; composing a translated noun into a translated template avoids depending on an instance being active at all.
- *Sharing `web-ui-kit`'s default `wuik-locale` storage key* — rejected: this org's own GitHub Pages topology puts every web app on one shared origin, so the shared key would leak a locale choice across unrelated apps, exactly the scenario `web-ui-kit`'s own documentation calls out as a reason to override it.
