## Modules
- [`modules/app.md`](modules/app.md) — application entry point, mounts the `web-ui-kit` app shell (a toolbar with the app title and a locale switcher, and into its `<main>` region, the lifebar folder input, the simulation controls, and the elements panel) into the DOM
- [`modules/input.md`](modules/input.md) — folder-based lifebar input: gathers files (directory picker or dropped folder), detects candidates, resolves which to load, reads and parses it, renders the picker/selection/status UI; once the lifebar loads, also resolves its sprite sheet from the same gathered files
- [`modules/lifebar.md`](modules/lifebar.md) — the lifebar `.def`-style format itself: a generic, unevaluated data model and its text parser
- [`modules/wasm.md`](modules/wasm.md) — bridge to the sibling `sff` library's WebAssembly build: loads a sprite sheet's metadata and batch-decodes sprite pixels, distinguishing a WASM-startup failure from a WASM-reported parse error
- [`modules/elements.md`](modules/elements.md) — the elements panel: lists every recognized element and draws a live composite preview, using sprite layers computed from each section's own `pos`/`N.spr`/`N.offset` entries, plus any simulated value's diagnostic overlay
- [`modules/simulation.md`](modules/simulation.md) — live value simulation controls: detects simulatable life/power/combo sections, renders their sliders/numeric inputs, and draws each value's diagnostic overlay in the preview
- [`modules/document.md`](modules/document.md) — in-memory representation of the currently loaded lifebar file and resolved sprite sheet, read from by the elements panel
- [`modules/scripts.md`](modules/scripts.md) — dev-tooling scripts, e.g. downloading the `sff` WASM release build
- [`modules/i18n.md`](modules/i18n.md) — this app's localization setup: wires the shared `web-ui-kit` i18next integration layer under its own namespace, plus a `t()` wrapper that falls back to a plain interpolated default value before the app has initialized

## Observed patterns
- TypeScript with `strict`, `noUnusedLocals`, `noUnusedParameters` enabled (`tsconfig.json`)
- Explicit `.ts` extensions on relative imports (`allowImportingTsExtensions`)
- Test files co-located with source as `*.test.ts`, using Vitest + jsdom
- Runtime checks (e.g. whether an external stylesheet actually loaded) are exposed as an injectable option so tests can force each branch deterministically, instead of relying on real network/CSS timing
- A format this app doesn't fully interpret is modeled as an ordered list of raw, unevaluated key/value entries per section, and sections are excluded (with a warning) rather than modeled if their name isn't recognized — deliberately diverging from `lifebar-editor`'s own silent-retain-everything parser for the same format, since this app never writes a file back (`.vibe/decisions/002`)
- Sections/entries are ordered arrays, never a `Record`/`Map`, so a duplicate section or key name (a real authoring pattern in hand-edited files) is never silently collapsed
- A non-standard, Chromium-originated browser API this app depends on (`FileSystemEntry`/`FileSystemDirectoryReader` for folder drag-and-drop) is wrapped behind a small local interface (`EntryLike`) covering only the members actually used, so the walk logic can be unit-tested against plain mock objects instead of requiring jsdom to implement the real thing
- File bytes/text are read via `FileReader` (`readAsText` for the lifebar file, `readAsArrayBuffer` for the sprite sheet) rather than `Blob` read methods, since the project's pinned jsdom version has an incomplete `Blob` implementation — the same real-browser/jsdom parity concern recurs across every OpenKakutou editor/viewer app
- The DOM-building logic of a screen/component is a pure exported function (`renderApp(root, version, options?)`, `renderLifebarFolderInput(root, options)`) taking its target element and data/callbacks as parameters, kept separate from the module-level bootstrap
- Every interactive control in the folder input view is a real native element (file input, radio inputs) or `web-ui-kit`'s own styled equivalent (`<wuik-button>`, org-wide UX audit backlog item 012) rather than a custom `role="button"` div, so keyboard operability comes for free with no bespoke keydown handling; the candidate-selection radios stay native since this kit has no radio-group component yet (tracked as `web-ui-kit` backlog item 014)
- `.click()` on a radio input reliably toggles `.checked` but doesn't reliably synthesize a `"change"` event under this project's pinned jsdom — read the selection from a `"click"` listener instead, the same workaround `character-viewer-web`'s animation player uses
- Module-level, in-process application state with no external effect to substitute in tests (`src/document/lifebar-document-store.ts`, `src/document/sff-sprite-sheet-store.ts`) is a plain get/set pair with a test-only reset function, mirroring `lifebar-editor`'s own equivalents
- A secondary resource genuinely owned by an already-loaded primary one (the sprite sheet a lifebar references) is resolved from the exact same already-gathered file listing rather than a second, separate input control — a lifebar pack bundles both in one folder, so a second picker would ask the user to re-select something already read (`.vibe/decisions/003`)
- A WASM bridge (`wasm/bridge.ts`) loads `wasm_exec.js` via injectable fetch + `new Function(source)()` (works identically in a real browser and jsdom/Node) and calls `go.run(instance)` without awaiting it (the Go runtime's `main()` never returns), memoizing instantiation across calls — ported field-for-field from `lifebar-editor`'s own bridge to the same `sff` WASM module
- A WASM bridge call returns a typed `{ok, ...} | {ok: false, error}` result for a *module-reported* error, but *rejects* (doesn't catch) if bringing the module itself up fails (fetch/instantiate) — the caller (`sprite-sheet-folder-input.ts`) wraps the call in its own try/catch to distinguish a setup-error from a parse-error rather than the bridge doing it for them
- A WASM-dependent module's tests run against the real downloaded build (`public/wasm/`, fetched via `npm run wasm:download`) plus a small real fixture file copied into the app's own `testdata/`, not a mocked WASM module
- Selection/highlight state for a canvas-based preview is a positioned DOM overlay `<div>` per selectable region, not a canvas redraw — a real element gets hover/focus/title affordances for free, and toggling a highlight never requires re-blitting the whole scene (`elements-panel.ts`, `.vibe/decisions/004`)
- Three distinct unresolved states (no data source loaded yet, an invalid/malformed reference, and "not applicable by design") are modeled and styled separately rather than collapsed into one generic "placeholder" or "error" — a diagnostic previewer's value is telling the user which case they're in (`element-layout.ts`'s `LayerResolution`, `.vibe/decisions/004`)
- A box/region computed from potentially-malformed source data (an element's overall highlight, unioned from its sprite layers) is clamped to a fixed canvas rectangle before use, so one wild/corrupt value in the source data can't distort or displace the result (`clampBoxToCanvas`)
- A DOM effect jsdom doesn't implement at all (`HTMLCanvasElement.getContext("2d")`, always throwing/returning null) is exposed as its own injectable option (`getContext2d`) separate from the draw-call injection (`drawSprite`) it gates, so a test can supply a fake non-null context object to observe draw calls without a real canvas — one level more granular than `sprite-browser.ts`'s own `drawPixels`-only seam in the sibling `lifebar-editor` repo, needed here because one canvas is shared across many draws instead of one canvas per sprite
- A slider (`web-ui-kit`'s `<wuik-slider>`) is always paired with a native numeric input for the same value, kept in sync on every change — a slider alone can't hit a precise diagnostic value and fails keyboard-only operability (`simulation-controls.ts`)
- A `web-ui-kit` component consumed in application code (`<wuik-slider>`, `<wuik-button>`) is driven through its documented attribute/event contract (`min`/`max`/`value` attributes, the `wuik-input` event) rather than the native `<input>` IDL properties or events it happens to wrap internally — its own unit test file doesn't register the real custom element (no side-effect import of `@openkakutou/web-ui-kit`), so it asserts against attributes and dispatches the component's own custom events directly, the same structural-only testing split `elements-panel.test.ts` already uses for `<wuik-panel>`
- When several equally-valid file candidates are gathered for a resource that should auto-resolve, an already-parsed sibling document's own declared reference (not just candidate count) is consulted to disambiguate before giving up and asking the user — the lifebar's own `[Files]`/`sff` entry picks the right sprite sheet among several `.sff` candidates (`sprite-sheet-folder-input.ts`)
- The "skip, don't block" precedent for unrecognized content applies at the line level too, not just the section level: a line that doesn't parse as `key = value` only hard-errors when it's inside a *recognized* section this app actually models — anywhere else (before any header, inside a skipped/unrecognized section) it's silently ignored, since real files carry content this app never models at all (embedded animation blocks, free-form banner text) (`parse.ts`)
- A synthetic/diagnostic overlay (not real rendering) uses its own dedicated color token, never one already meaning something else on the same screen (selection, an unresolved reference) — so the two cues stay visually distinguishable when both are visible on the same element at once (`simulation-overlay.ts`, `.vibe/decisions/005`)
- A recognized-name pattern list supports two real-world naming conventions for the same concept side by side, additively, rather than replacing one with the other — the classic MUGEN per-player-prefixed section names and the modern Ikemen GO generic ones both stay recognized (`known-sections.ts`); a variant qualifier (Simul/Turns/Tag mode prefixes) is only added to the specific families real files were actually observed combining it with, not applied uniformly by assumption (`.vibe/decisions/006`)
- A translation wrapper (`i18n.ts`'s `t(key, defaultValue, vars?)`) returns the interpolated `defaultValue` verbatim whenever this app hasn't initialized i18n yet in the current page, mirroring `web-ui-kit`'s own `t()` contract — every call site's `defaultValue` matches its English catalog entry exactly, so a render is identical whichever path it takes and the large majority of existing tests never need to bootstrap i18n at all (`.vibe/decisions/007`)
- `initAppI18n` is only ever called from the real bootstrap (`main.ts`'s `mount()`), awaited before the first render — never from the synchronous, directly-testable render functions themselves
- A long-lived view that must keep its currently-displayed status text live across a locale change re-formats it from a small stored status descriptor (a tagged variant plus its raw parameters) rather than a pre-formatted string, so a language switch re-translates it without re-running the load/parse that produced it (`lifebar-folder-input-view.ts`'s `MainStatus`/`SpriteStatus`, `.vibe/decisions/007`)
- A locale-change subscription owned by a render function that itself gets re-invoked often (`renderApp`, called once for real but repeatedly in tests) is torn down and re-made at the very top of every call via a module-level "current unsubscribe" variable, rather than left to accumulate — the same replace-not-accumulate shape the sibling `lifebar-editor` repo already uses for its own render-owned live subscription
- Pluralized text ("1 section" vs "3 sections") is composed by picking an already-translated singular/plural noun and interpolating it into a translated sentence template, not i18next's automatic `_one`/`_other` key-suffix pluralization — the fallback path (before `initAppI18n` resolves) only does simple `{{var}}` substitution and can't evaluate CLDR plural rules (`.vibe/decisions/007`)
- An npm dependency whose installed version ships no `.d.ts` of its own (`@openkakutou/web-ui-kit`) is typed locally with a scoped ambient `declare module` (`src/types/web-ui-kit.d.ts`) covering only what this app actually imports by name, the same approach the sibling `lifebar-editor` repo already took for the same gap — importing a type from a third package (`i18next`) at the top of that same ambient file, even type-only and unused, was confirmed by bisection to make `tsc` silently fail to merge the `declare module` block at its real import site, so the file defines its own small structural `I18nInstance` interface instead of importing `i18next`'s
- This app passes its own `storageKey` to `initI18n` rather than sharing `web-ui-kit`'s default: every OpenKakutou web app deploys as its own GitHub Pages project site under the same origin, and `localStorage` is scoped per-origin, not per-path, so the shared default key would leak one app's language choice into every other one (`.vibe/decisions/007`)
