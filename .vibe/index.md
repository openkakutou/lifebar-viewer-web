## Modules
- [`modules/app.md`](modules/app.md) — application entry point, mounts the `web-ui-kit` app shell (and, into its `<main>` region, the lifebar folder input) into the DOM
- [`modules/input.md`](modules/input.md) — folder-based lifebar input: gathers files (directory picker or dropped folder), detects candidates, resolves which to load, reads and parses it, renders the picker/selection/status UI; once the lifebar loads, also resolves its sprite sheet from the same gathered files
- [`modules/lifebar.md`](modules/lifebar.md) — the lifebar `.def`-style format itself: a generic, unevaluated data model and its text parser
- [`modules/wasm.md`](modules/wasm.md) — bridge to the sibling `sff` library's WebAssembly build: loads a sprite sheet's metadata and batch-decodes sprite pixels, distinguishing a WASM-startup failure from a WASM-reported parse error
- [`modules/document.md`](modules/document.md) — in-memory representation of the currently loaded lifebar file and resolved sprite sheet, for a later screen to read from
- [`modules/scripts.md`](modules/scripts.md) — dev-tooling scripts, e.g. downloading the `sff` WASM release build

## Observed patterns
- TypeScript with `strict`, `noUnusedLocals`, `noUnusedParameters` enabled (`tsconfig.json`)
- Explicit `.ts` extensions on relative imports (`allowImportingTsExtensions`)
- Test files co-located with source as `*.test.ts`, using Vitest + jsdom
- Runtime checks (e.g. whether an external stylesheet actually loaded) are exposed as an injectable option so tests can force each branch deterministically, instead of relying on real network/CSS timing
- A format this app doesn't fully interpret is modeled as an ordered list of raw, unevaluated key/value entries per section, and sections are excluded (with a warning) rather than modeled if their name isn't recognized — deliberately diverging from `lifebar-editor`'s own silent-retain-everything parser for the same format, since this app never writes a file back (`.vibe/decisions/002`)
- Sections/entries are ordered arrays, never a `Record`/`Map`, so a duplicate section or key name (a real authoring pattern in hand-edited files) is never silently collapsed
- A non-standard, Chromium-originated browser API this app depends on (`FileSystemEntry`/`FileSystemDirectoryReader` for folder drag-and-drop) is wrapped behind a small local interface (`EntryLike`) covering only the members actually used, so the walk logic can be unit-tested against plain mock objects instead of requiring jsdom to implement the real thing
- File bytes/text are read via `FileReader` (`readAsText` for the lifebar file, `readAsArrayBuffer` for the sprite sheet) rather than `Blob` read methods, since the project's pinned jsdom version has an incomplete `Blob` implementation — the same real-browser/jsdom parity concern recurs across every OpenKakutou editor/viewer app
- The DOM-building logic of a screen/component is a pure exported function (`renderApp(root, version, options?)`, `renderLifebarFolderInput(root, options)`) taking its target element and data/callbacks as parameters, kept separate from the module-level bootstrap
- Every interactive control in the folder input view is a real native element (file input, radio inputs, buttons) rather than a custom `role="button"` div, so keyboard operability comes for free from the browser with no bespoke keydown handling
- `.click()` on a radio input reliably toggles `.checked` but doesn't reliably synthesize a `"change"` event under this project's pinned jsdom — read the selection from a `"click"` listener instead, the same workaround `character-viewer-web`'s animation player uses
- Module-level, in-process application state with no external effect to substitute in tests (`src/document/lifebar-document-store.ts`, `src/document/sff-sprite-sheet-store.ts`) is a plain get/set pair with a test-only reset function, mirroring `lifebar-editor`'s own equivalents
- A secondary resource genuinely owned by an already-loaded primary one (the sprite sheet a lifebar references) is resolved from the exact same already-gathered file listing rather than a second, separate input control — a lifebar pack bundles both in one folder, so a second picker would ask the user to re-select something already read (`.vibe/decisions/003`)
- A WASM bridge (`wasm/bridge.ts`) loads `wasm_exec.js` via injectable fetch + `new Function(source)()` (works identically in a real browser and jsdom/Node) and calls `go.run(instance)` without awaiting it (the Go runtime's `main()` never returns), memoizing instantiation across calls — ported field-for-field from `lifebar-editor`'s own bridge to the same `sff` WASM module
- A WASM bridge call returns a typed `{ok, ...} | {ok: false, error}` result for a *module-reported* error, but *rejects* (doesn't catch) if bringing the module itself up fails (fetch/instantiate) — the caller (`sprite-sheet-folder-input.ts`) wraps the call in its own try/catch to distinguish a setup-error from a parse-error rather than the bridge doing it for them
- A WASM-dependent module's tests run against the real downloaded build (`public/wasm/`, fetched via `npm run wasm:download`) plus a small real fixture file copied into the app's own `testdata/`, not a mocked WASM module
