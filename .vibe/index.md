## Observed patterns
- TypeScript with `strict`, `noUnusedLocals`, `noUnusedParameters` enabled (`tsconfig.json`)
- Explicit `.ts` extensions on relative imports (`allowImportingTsExtensions`)
- Test files co-located with source as `*.test.ts`, using Vitest + jsdom
- Runtime checks (e.g. whether an external stylesheet actually loaded) are exposed as an injectable option so tests can force each branch deterministically, instead of relying on real network/CSS timing
- A format this app doesn't fully interpret is modeled as an ordered list of raw, unevaluated key/value entries per section, and sections are excluded (with a warning) rather than modeled if their name isn't recognized — deliberately diverging from `lifebar-editor`'s own silent-retain-everything parser for the same format, since this app never writes a file back (`.vibe/decisions/002`)
- Sections/entries are ordered arrays, never a `Record`/`Map`, so a duplicate section or key name (a real authoring pattern in hand-edited files) is never silently collapsed
- A non-standard, Chromium-originated browser API this app depends on (`FileSystemEntry`/`FileSystemDirectoryReader` for folder drag-and-drop) is wrapped behind a small local interface (`EntryLike`) covering only the members actually used, so the walk logic can be unit-tested against plain mock objects instead of requiring jsdom to implement the real thing
- File bytes/text are read via `FileReader` (`readAsText`) rather than `Blob` read methods, since the project's pinned jsdom version has an incomplete `Blob` implementation — the same real-browser/jsdom parity concern recurs across every OpenKakutou editor/viewer app
- The DOM-building logic of a screen/component is a pure exported function (`renderApp(root, version, options?)`, `renderLifebarFolderInput(root, options)`) taking its target element and data/callbacks as parameters, kept separate from the module-level bootstrap
- Every interactive control in the folder input view is a real native element (file input, radio inputs, buttons) rather than a custom `role="button"` div, so keyboard operability comes for free from the browser with no bespoke keydown handling
- `.click()` on a radio input reliably toggles `.checked` but doesn't reliably synthesize a `"change"` event under this project's pinned jsdom — read the selection from a `"click"` listener instead, the same workaround `character-viewer-web`'s animation player uses
- Module-level, in-process application state with no external effect to substitute in tests (`src/document/lifebar-document-store.ts`) is a plain get/set pair with a test-only reset function, mirroring `lifebar-editor`'s own `lifebar-document-store.ts`
